Camera — the thing that actually breaks

This is the failure DEV-46128 is about. Presence of the API means nothing — only calling it does. Expect a permission prompt; allow it. The log records the exact error name if it fails.

Replicate the document widget

Same sequence as the real widget: getUserMedia with the app's own constraints (ideal 1920×1080), then srcObject, then play(). K uses the back camera like the document steps, L the front one like the selfie step. Switching releases the previous camera first and then reports which one it actually got — if a plain facingMode is ignored it retries with an exact one.

Leave the webview (Android)

This is what the app ships. Android hands the link to the default browser; the “Open with” chooser only appears when no default is set, and a page cannot force it. Forcing a vendor (package=com.android.chrome) was tried too and behaved identically on a phone whose default is Chrome, so it was dropped — it would only ignore the client’s own choice.

Leave the webview (iOS experiments)

Both are undocumented. Expected to do nothing in Facebook / Instagram — the point is to find out for certain instead of assuming.

Copy the link

 

One button, the chain the app itself will use: navigator.clipboard.writeText first, and an execCommand fallback if it is missing, rejects, or never answers — every step is logged. “COPIED” only means the API did not complain; I reads the clipboard back, which is the only real proof, but in-app browsers often deny it (Facebook always does). iOS may ask for permission to paste; allow it.
